# 專案憲法

本文件整理跨任務使用的固定規則。每次執行的材料與輸出位置由 `workflow/` 指定；各任務的完整驗收條款以 `standard-cards/` 為準。本文件不取代或刪減 Standard Cards。以下路徑皆以 repo 根目錄為基準。

重建學習成果的提示詞與 Standard Card 對實際輸出的要求不一致時，以 Standard Card 為準。

## 01 PROJECT GOAL｜專案目標

把課程材料轉成能幫助理解、判斷與實作的學習筆記，再轉成能獨立閱讀、解決讀者問題的技術 Blog 草稿。

將反覆試用後確認有效的要求保存在提示詞與 Standard Cards，讓換課程、換 Agent 時仍能依同一套流程與標準執行，減少重新交代與逐段修正的負擔。

## 02 INPUT｜輸入

- `課程材料/` 下的每個檔案代表一份獨立材料，每份材料對應一份學習成果輸出（`output/預期學習成果/`）與一份 Blog 輸出（`output/blog/`）。
- `workflow/` 保存對應提示詞與「產出對應表」，記錄每份材料與兩份輸出的對應路徑。新增或更換課程時，只需把材料放進 `課程材料/`，不必手動修改 workflow 中的檔名；對應表由 Agent 在產出完成後自動更新。
- 重建學習成果：從 `課程材料/` 讀取逐字稿或課程材料，搭配確認階段使用者選填的額外課程筆記（預設為無）；課程名稱未另外指定時，由 Agent 依材料內容或檔名自動推導。
- 轉成 Blog：以該份材料已產出的學習筆記為主要依據，搭配原始課程材料，以及確認階段向使用者詢問取得的實作經驗或想法（預設為無）。
- 標示「（無）」或未提供的選填輸入視為未提供，不自行補造。

## 03 REQUIRED PROCESS｜必要流程

1. 先讀取本次 `workflow/` 的「產出對應表」，並只列出 `課程材料/` 與 `output/` 的檔案清單（僅比對檔名，**確認前不讀取 `課程材料/` 或 `output/` 的檔案內文**，避免材料眾多或篇幅過長時卡在讀取等待），向使用者回報最新狀態並確認本次要處理的項目：
   - **已有對應輸出**：詢問是否重新跑一次流程（覆蓋或重新產出）或跳過該份材料；取得確認後才執行，不自行重跑覆寫。
   - **僅完成學習成果、尚無 Blog 輸出**：執行整套流程或 Blog workflow 時，詢問要直接以既有學習筆記接續產出 Blog，還是從學習成果重新跑起。
   - **尚無對應輸出**：列出新材料檔名，與上述項目一併請使用者確認本次要處理哪些材料。
   - **詢問選填補充內容**：執行學習成果時一併詢問有無額外課程筆記；執行 Blog 時一併詢問有無想加入的個人實作經驗或想法（兩者預設皆為「無」）。
   取得使用者確認後，再讀取本文件、對應提示詞、同名 Standard Card，以及本次選定要處理的材料內文。
2. 重建學習成果時，結合 UbD、Cornell Notes 與 Self-explanation，找出核心問題，依材料實際支持的能力推導預期學習成果（原則上 3～5 個，不為湊數拆分或過度推論）及其材料依據，依知識與能力的關係整理筆記，設計理解、應用與實作三類自我驗證題目，整理尚未解決的問題。具體分析步驟依對應提示詞執行。
3. 轉成 Blog 時，提出兩個切入角度，選擇證據最充足、最容易實作驗證的角度，建立通用思考架構與「問題—解法—驗證—回顧」大綱，再撰寫文章。
4. 完整執行時，寫入前對照來源並逐條檢查 Standard Card。不符合時，優先針對違規處及因本次修改而失準的相依內容（如標題、驗證題、來源定位）做最小範圍修正，保留與違規無關且已通過的內容與結構，不為潤飾無故重寫；每次修改後，仍須對最新完整輸出從頭檢查全部條款，全部通過才寫入指定位置。局部修正僅適用於同一輪修稿；使用者要求重跑或執行流程驗證新輪次時，須重新產出。寫入後若再次複核發現漏判，修正已寫入的內容並從頭重新驗收；持續修正到最新版本全部通過。保留首次漏判的紀錄，不把後來的通過說成首次寫入前已通過。部分執行或使用者明確要求本次例外時，依第 05 節判定。

只執行使用者指定的 workflow 或其中一部分，遵守指定停點。每份輸出通過驗收並寫入 `output/` 後，由執行 Agent 自動將材料與實際產出路徑更新至 `workflow/` 的「產出對應表」（完成學習成果時，一併同步至 `workflow/blog/workflow-轉成blog.md` 的對應表）。單獨執行 Blog 時，從對應表讀取該材料已設定的學習筆記。

使用者要求驗證流程時，依 `docs/流程驗證.md` 執行。該程序的案例設定取代本次輸入、輸出與 Blog 銜接路徑；直接傳遞本次學習成果路徑，不寫回正式 workflow。其他提示詞與 Standard Card 要求照常適用。

## 04 OUTPUT CONTRACT｜輸出約定

### 學習成果

- 寫入 `output/預期學習成果/`，使用能概括課程主題的繁體中文檔名。
- 保留四個區塊：A. 課程核心、B. 學習筆記、C. 自我驗證、D. 尚未解決的問題。
- 內文直接呈現知識。提示詞中的思考項目不直接變成欄位標籤；不附上分析過程或驗收檢查表。
- D 區塊每點依結論、原因、證據撰寫。

### Blog

- 寫入 `output/blog/`，使用能概括文章主題的繁體中文檔名。
- 文章區在前，從文章標題開始；寫作過程區在後，以 `# 寫作過程` 開頭，兩區用 `---` 分隔。
- 寫作過程區依序包含：文章選題分析、文章定位、Markdown 文章大綱、思考架構、內容來源區分、待補充項目。

各項格式與文字限制依對應提示詞及 Standard Card 執行。

只執行部分工作時，結果回報於對話或寫入使用者指定的位置；未另有明確指示，不覆寫 workflow 的完整產出檔案，並說明整份 workflow 尚未完成。

## 05 DEFINITION OF DONE｜完成定義

- 完整執行時，本次指定 workflow 的必要流程與輸出區塊已完成，檔案已寫入指定位置。
- 對應 Standard Card 的每一條均已檢查並通過：
  - 學習成果：`standard-cards/預期學習成果/從課程內容重建學習成果.md`
  - Blog：`standard-cards/blog/把學習成果轉成blog.md`
- 必要技術細節與原意受到保留，結論的確定程度符合材料證據；推論及未測試內容沒有被寫成既定事實或已完成結果。

若寫入後發現漏判，依第 03 節修正並重新驗收；以最新版本全部通過作為完成判定。先前不合格的版本與修正經過，在流程驗證時保留於工作紀錄，不因最終通過而抹去。

只執行部分工作時，檢查適用條款，完成該部分不代表整份 workflow 通過。使用者明確要求本次偏離某條標準時，依要求執行並回報例外條目，其餘適用條款仍須全部通過；不得把例外宣稱為原標準已通過，也不自動修改 Standard Card。

逐條驗收由執行 Agent 自行判斷。日常產出不包含獨立審查或另存 Pass／Fail 報告；流程驗證依驗證程序另存結果。Standard Card 中的「訂這條的原因」說明標準的由來，不是本次驗收結果。

## 06 MUST NOT｜禁止事項

- 需求依據為使用者明確要求，以及 `prompts/`、`standard-cards/`、`workflow/` 的現有文字。課程作業說明或老師示範中的範例值，例如字數上限、標準條數，未經上述來源採用，不當成本專案需求。
- 不虛構來源、個人經驗、測試結果或數據。學習筆記不為潤飾補入材料沒有的情境、例子或論點；AI 推論與 Blog 延伸分析依各自 Standard Card 處理，不冒充課程原意或既定事實。
- 未經使用者明確要求，不刪改任何 Standard Card 的條款、例子與「訂這條的原因」。使用者只要求調整呈現方式時，保留原條款文字、順序與分類。
- 不把驗收標籤或檢查結果塞進學習筆記，也不讓寫作過程與 Blog 文章交錯出現。
- 不擅自擴大修改範圍、跨過指定停點，或新增未要求的版本與檔案。

## 07 FAILURE BEHAVIOR｜失敗處理

- **失敗先定位：** 對照來源、Standard Card 與執行指示，指出失敗內容及對應條文。已有明確要求卻未遵守時，修正輸出；指示缺漏、含糊或與卡衝突時，提出提示詞、workflow 或憲法的最小修正，經使用者確認後保存。若已有明確授權，依授權範圍執行。不得為了通過驗收而放寬標準卡。修正規則後，依 `docs/流程驗證.md` 重跑失敗案例與原先通過的案例；完成文件修改不代表問題已解決。
- **標準未通過：** 依必要流程修正與重檢。寫入前未全部通過，不寫入指定輸出；寫入後才發現漏判，就修正已寫入的內容並重新驗收。最新版本仍未通過時，不宣稱完成。本次明確例外與部分執行依第 05 節處理。
- **材料不足或有疑點：** 先核對提供的材料，只寫材料能支持的範圍，不用推論補滿。局部辨識錯誤或矛盾仍無法釐清時，避開不確定內容；只要仍能符合標準，就繼續執行。
- **缺口的呈現：** 學習成果中值得追究的知識問題依 D 區塊格式處理，不另立「材料限制」或「逐字稿疑點」段落；Blog 的缺口放在寫作過程區。
- **無法繼續：** 以下情況停止受影響的 workflow，不寫入輸出、不宣稱完成，並回報受阻檔案或具體 Standard 條目、原因及需要補充的材料或決定：
  - workflow、指定提示詞、對應 Standard Card，或已指定且未標示「（無）」的輸入檔無法讀取。
  - 已縮小範圍並修正，仍有具體條款因缺少必要材料而無法符合。
  - 要求互相衝突，且無法依學習成果的卡優先規則，或使用者明確的本次要求解決。
- **反覆修正仍失敗：** 可自行修正的文字問題先繼續修正；確實無法通過時，據實回報未通過的條款、已嘗試的修正與仍失敗的原因。不自行放寬標準；未寫入時不寫入，已寫入的版本保留為未通過的證據，不宣稱完成。
- **串接受阻：** 本次學習成果未完成時，不接續執行 Blog，也不自行改用上一版學習筆記。
- **使用者指出偏離期待：** 依指定範圍修正，不順帶修改範圍外內容。將修正沉澱為新標準時，依使用者明確指示更新 Standard Card。

## 08 RULE CHANGES｜規則修改連動檢查

同一條規則常同時涉及憲法、提示詞、Standard Card 與 workflow。修改 `CLAUDE.md`、`AGENTS.md`、`docs/`、`prompts/`、`standard-cards/`、`workflow/` 的規則時（單純更新 workflow 產出對應表的資料列除外）：

1. 先對照下表檢查相關文件與段落：

| 修改的內容 | 一併檢查的關聯位置 |
| --- | --- |
| 學習成果的步驟、數量、A–D 區塊 | 學習成果提示詞「分析步驟」「輸出格式」；本文件 03 第 2 點、04「學習成果」；學習成果卡；Blog 提示詞「一、輸入資料與使用規則」 |
| Blog 選題、大綱、寫作過程區架構 | Blog 提示詞二～四；本文件 03 第 3 點、04「Blog」；Blog 卡 |
| 驗收、修正、重檢、寫入時機 | 本文件 03 第 4 點、05、07；兩份提示詞「驗收標準」；`docs/流程驗證.md` 第 2、4 節 |
| 執行前盤點與確認、選填輸入 | `CLAUDE.md` 與 `AGENTS.md`「執行 workflow 時」；本文件 03 第 1 點；兩份 workflow「執行方式」 |
| 路徑、檔名、對應表欄位 | 兩份 workflow「固定設定」「產出對應表」；本文件 02、03 末段、05；`CLAUDE.md` 與 `AGENTS.md` 目錄說明 |

2. 搜尋舊規則關鍵字、數字與同義寫法（排除 `Sample Code/`、`docs/工作紀錄/` 歷史快照與 `output/`），逐一判定每個關聯處為「需同步修改」「已相容無須修改」或「觸及 Standard Card 需使用者授權」。
3. 觸及 Standard Card 但使用者未明確要求改卡時，依第 06 節不自動修改，先回報衝突交由使用者決定。
4. 完成修改後，確認 `CLAUDE.md` 與 `AGENTS.md` 保持一致，並於回報與 commit 訊息說明連動檢查結果，不另建變更紀錄檔。改變執行行為時依 `docs/流程驗證.md` 驗證。
