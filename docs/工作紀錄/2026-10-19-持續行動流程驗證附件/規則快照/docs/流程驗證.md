# 流程驗證

用新的正常材料與容易出錯的案例，確認「課程材料 → 學習成果 → Blog」能在相同標準下重複執行。建立流程、首次使用新類型材料或修改執行規則時使用；日常產出依原 workflow 執行。

驗收依據為現有兩張 Standard Card，保留其全部條文、例子、分類及訂立原因。這份程序只定義如何驗證與改善流程，不複製或放寬標準。

## 1. 準備案例與執行設定

先讀 `docs/project-constitution.md`，再讀以下 workflow、各自引用的提示詞與 Standard Card：

- `workflow/預期學習成果/workflow-重建學習成果.md`
- `workflow/blog/workflow-轉成blog.md`

準備兩個案例：

- **正常案例：** 使用不同於上一份作業原始輸入的新課程材料。沒有新材料時，先完成可獨立進行的文件工作，回報缺少的材料並向使用者取得路徑；不得把重跑舊材料當成新案例通過。
- **特殊案例：** 優先選取材料中容易忽略的限制、反例、不確定資訊或辨識錯誤。若需製作測試變體，另存檔案，保留原文並記錄變更，不改動原始材料，也不把測試變體冒充真實逐字稿。

每個案例執行前，填妥下列設定。設定存入本次驗證紀錄，新 Session 從紀錄讀取，不靠前次對話補充。

| 欄位 | 設定內容 |
| --- | --- |
| 案例識別與輪次 | 使用不重複的名稱，包含日期、案例與執行次數 |
| 課程名稱與輸入 | 課程名稱、筆記、逐字稿、實作經驗或想法的實際路徑；未提供者填「（無）」 |
| 驗證範圍 | 預設學習成果與 Blog；若只驗證其中一段，明寫範圍，不宣稱整條流程通過 |
| 預期行為 | 要產出什麼或在何處停止、應保留的來源內容、對應的卡條文或憲法條文 |
| 輸出位置 | 學習成果與 Blog 分別存入原用途子目錄，檔名用 `驗證-<案例與輪次>-<繁中主題>.md` |

案例設定只取代本次 workflow 的課程名稱、輸入與輸出位置，不改驗收要求。兩段串接時，將本次通過驗收的學習成果路徑直接交給 Blog，搭配同案例原始材料；不改寫正式 Blog workflow，不使用上一輪產出頂替。

記錄執行前的規則版本：已提交且無相關修改時記 commit；有未提交修改時，另存本次使用的憲法、提示詞、卡、workflow 與本程序快照於該次工作紀錄的附件目錄。記錄輸入及正式 workflow、卡、既有 output 的 SHA-256，供結束時比較。確認所有輸出路徑尚不存在，避免覆寫。

準備完成的條件：兩個案例的材料可讀、範圍與預期明確、輸出不會覆蓋既有檔案、規則版本可還原。

## 2. 執行正常案例

建議開新 Session，只提供本程序與本次驗證紀錄的路徑，由 Agent 讀取指定的規則與材料。記錄是否使用新 Session；同一 Session 的結果不能當成跨 Session 驗證證據。使用其他 Agent 時，遵守專案的協作授權規則。

依原提示詞先產出學習成果，對照來源並逐條檢查對應卡，通過才寫入案例指定位置。再以該檔執行 Blog，依 Blog 卡逐條驗收，通過才寫入。前段受阻時依憲法停止串接。

記錄實際結果、產出路徑及支撐驗收結論的來源與產出位置。有失敗時，先記下失敗條文和具體內容，再依第 4 節處理；不能只留下修好後的「通過」。驗收結果不寫進卡或學習成果。

## 3. 執行特殊案例

使用特殊案例的設定，依第 2 節執行。建議另開新 Session，避免沿用正常案例的回答。

逐條驗收之外，特別核對事前指定的限制、反例或疑點是否正確處理。案例若預期停止，確認停止位置、回報原因及未寫入輸出等行為符合憲法；正確停止可算此案例通過，不代表完整內容產出通過。

## 4. 定位失敗與修正

依憲法「失敗先定位」處理。每個問題記錄對應條文、具體偏差及分類依據：

- **執行偏差：** 規則已寫明，輸出未遵守。局部修正輸出，再依原流程完整重檢。
- **指示缺陷：** 提示詞、workflow 或憲法缺漏、含糊或與卡衝突。提出最小修正，依授權保存到相應文件，接著執行第 5 節。
- **材料缺口：** 按憲法縮小可支持範圍或回報受阻。不要因為缺少材料就放寬標準；補齊材料後再跑。

若無法判斷原因，記錄待釐清之處，不強行歸類。沒有失敗就記錄通過，不為完成驗證而硬改規則。

## 5. 修改規則後重新執行

保存修改前後的規則版本及修改理由。使用相同案例輸入與驗收標準、新的輪次與輸出路徑，重新執行原失敗案例及先前通過的正常案例；建議使用新 Session。

重新對照來源和全部適用卡條文，確認原問題已解決，原先通過的內容品質仍保留。文字不必逐字相同；比較的是正確性、必要內容與標準是否仍符合。再次失敗則回到第 4 節，無法繼續時依憲法回報，不宣稱完成。

## 6. 保存結果與判定完成

每次驗證在 `docs/工作紀錄/<日期>-<驗證名稱>.md` 留一份紀錄，包含上述案例設定與以下六項。重跑結果追加於同份紀錄，保留先前結果。

| 項目 | 記錄內容 |
| --- | --- |
| 輸入 | 案例來源、檔案路徑及雜湊、測試變體差異、驗證範圍 |
| 規則版本 | commit 或快照位置；執行前正式檔案雜湊 |
| 預期 | 案例預期行為及對應條文 |
| 實際 | Session 使用情況、輸出路徑、驗收依據、失敗內容或受阻原因 |
| 修正 | 原因分類、修正位置與理由；無修正則寫「無」 |
| 重跑 | 各輪結果、原問題及既有品質的檢查結論；未執行須寫明原因 |

完成條件：正常及特殊案例符合事前預期；每個失敗都有處理結果；若改規則，原失敗案例與正常案例重跑通過。比對執行前後正式檔案內容或雜湊，確認未發生未授權變更；獲准的規則修改另列差異。`git status` 只輔助檢查，不能取代內容比對。

文件與路徑檢查通過只代表程序可供執行。缺新材料、未實跑或尚有受阻案例時，記錄未完成項目，不宣稱流程驗證通過。
