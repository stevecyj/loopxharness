# Claude 提示詞最佳實踐

撰寫或修改 `prompts/`、`workflow/` 裡的檔案時遵守以下原則。

來源：
- [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)

## 寫清楚、寫具體

- 黃金法則：把提示詞拿給不了解背景的同事看，他看不懂的話，Claude 也看不懂。
- 說清楚輸出格式、限制和完成標準。步驟順序或完整性重要時，用編號清單。
- 想要超出基本要求的結果，就直接寫出來，不要指望模型自己推斷。
- 要它動手做就用祈使句，例如「修改這個函式」。「可以建議一些修改嗎？」這種問法通常只會得到建議。

## 說明原因

規則後面附上原因，Claude 能從原因推到其他情況。

- 較差：`NEVER use ellipses`
- 較好：`輸出會給 TTS 朗讀，TTS 無法發音刪節號，所以不要使用刪節號。`

## 範例

- 範例是控制格式、語氣和結構最可靠的方式，3–5 個效果最好。
- 範例要貼近實際用途，也要夠多樣，避免模型學到不該學的模式。
- 用 `<example>` 包起來（多個範例外層再包 `<examples>`），跟指示分開。

## 用 XML 標籤組織結構

指示、背景、範例和輸入混在一起時，分別包進 `<instructions>`、`<context>`、`<input>` 這類標籤。標籤名稱要一致、有描述性。有層級關係的內容就巢狀包起來。

## 給它驗證手段

- 附上可以跑的檢查，例如測試、build、lint，或可比對的預期輸出，並要求它「完成後執行檢查，失敗就修」。
- 要求附上證據（指令與輸出），不要只說「完成了」。

## 控制範圍

- 只做要求的事。不加額外功能，不加沒用到的抽象，也不加處理不可能發生情況的程式碼。
- 實作要能處理所有合法輸入，不要只為了讓測試通過而把值寫死。測試不合理時要回報。
- 沒讀過的檔案不下結論，先調查再回答。
- 不可逆或會影響別人的操作要先確認，例如刪檔、force push、對外發送。

## 強調要省著用

只在一直被忽略的那條規則加 `IMPORTANT`。到處都強調，就沒有一條會被注意到。

## 提示詞檔案要精簡

對每一行問自己：「刪掉它，Claude 會因此出錯嗎？」不會就刪。不要寫看程式碼就知道的事、通用常識，或「寫好一點」這類空話。
