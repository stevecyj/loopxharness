# 作業 #02：從修結果到修規則

以下整理專案現有規則與歷次實跑紀錄，這次沒有重跑 workflow。文中的規則是摘要，完整條款見連結。

## 1. 我的任務說明

我的任務是把課程逐字稿整理成學習筆記，再轉成讀者不必先看課程也能讀懂的 Blog 草稿。試跑時發現的問題，經修正、確認後寫進規則，讓換材料或換 Agent 時也能照同一套標準驗收。

## 2. Standard Card

學習成果與 Blog 各有一張驗收卡：

| 分類 | 學習成果 | Blog |
| --- | --- | --- |
| Must Have | 觀念有具體情境與重要原因，情境來自材料 | 文章可獨立閱讀，來源與待驗證事項可追溯 |
| Must Preserve | 保留必要細節，察覺辨識錯誤與矛盾 | 保留原意，區分課程內容與 AI 延伸 |
| Must Fit | 依知識與能力關係重組內容 | 正文在前、寫作過程在後；材料不足時縮小範圍 |
| Must Not | 不補造情境、論點，不把推論寫成事實 | 不虛構經驗、測試結果或數據，不逐段改寫逐字稿 |

完整條款保存在 [學習成果 Standard Card](../../standard-cards/預期學習成果/從課程內容重建學習成果.md) 與 [Blog Standard Card](../../standard-cards/blog/把學習成果轉成blog.md)。

## 3. Task Spec（Input / Process / Output / Must Not）

| 項目 | 規格 |
| --- | --- |
| Input | 課程逐字稿、選填課程筆記；轉成 Blog 時加入本輪學習成果與選填個人經驗 |
| Process | 盤點檔名與產出對應表 → 確認處理範圍 → 讀取材料與規則 → 重建學習成果 → 驗收 → 轉成 Blog → 驗收 → 寫入並更新對應表 |
| Output | 一份含 A～D 區塊的學習成果，以及一份含文章區、寫作過程區的 Blog |
| Must Not | 不擅自覆寫既有輸出、不為湊數補造內容、不將個人說法當成普遍事實、不將未實測的方法寫成已完成結果 |

流程驗證另用指定案例路徑，不更新正式 workflow 的產出對應表。

## 4. Project Rules（6 條）

1. 執行前先盤點檔名與對應表，確認材料、覆寫方式及補充內容後才讀取材料內文。
2. 學習成果依材料實際支持的能力整理，不為湊足數量拆分或增加論點。
3. 保留來源的限制、條件與確定程度，區分個人經驗、材料支持與 AI 推論。
4. 寫入前逐條驗收；修正後重新檢查完整輸出。
5. 寫入後發現漏判，修正並重新驗收，保留首次失敗紀錄。
6. 修改規則後，重跑失敗案例與原先通過的案例，不以文件改完作為問題已解決的證據。

## 5. 正常案例的執行結果

輸入完整的「從動機到持續行動」英文逐字稿，執行「學習成果 → Blog」。

筆記整理了啟動動機與持續系統的差異，以及環境、訊號、行為、回饋的操作方式。但 Agent 初次執行時，把部分個人觀點寫成普遍事實，加入材料未教的方法，還先寫入檔案才正式驗收。

修正後，主 Agent 複核內容並判定通過；首次執行的錯誤保留在工作紀錄中。

## 6. Edge Case 的執行結果

特殊案例只用 681 字元的「戰術性壓力」原文節錄。這段材料很短，當事人先說自己相信會無家可歸，隨後又澄清實際不會，適合用來測試 Agent 能否保留這個差別。

初稿曾把「當事人相信會無家可歸」寫成實際後果，也把「多次使用、個人認為有效」寫成反覆有效。

修正後，筆記與 Blog 分清了當事人的相信和實際處境，也保留「極端、不適合所有人」的限制。Blog 則帶讀者檢查一則成功經驗能支持哪些說法、適用到哪裡。

## 7. 發現的問題，以及修改了哪一條 Rule / Spec

試跑後，專案做過以下修改：

| 問題 | 修改位置與內容 |
| --- | --- |
| 驗收規則只描述寫入前檢查，沒說清楚寫入後發現錯誤要怎麼處理、何時算完成 | 修改專案憲法第 03、05、07 節、流程驗證程序及兩份提示詞：在同一輪修正後重新檢查全文，最新版本全部通過才算完成，並保留首次失敗證據 |
| Blog 用「健身的做法是……／創作的做法是……」反覆堆放例子，文字冗長 | 在 Blog Card 的 Must Not 新增限制：直接寫情境與動作，只保留有助於段落重點的細節 |
| 寫作過程的來源分類與待辦不夠一致，難以追查正文依據 | 更新 Blog 提示詞與 Card，固定來源分類、子區塊與欄位，要求查證或實作待辦指回對應的來源條目，說明完成後要修改文章的哪裡 |

至於把個人說法誇大成事實，原有條款已經禁止，這類錯誤直接修正輸出，再按原標準驗收。

## 8. 修改後重新執行的結果

依[驗證工作紀錄](../工作紀錄/2026-10-19-持續行動流程驗證.md)：

- 第 3 次依修改後的驗收規則重跑，正常與特殊案例的最後版本通過。
- 第 4 次重跑驗證文字密度新標準；正常 Blog 正文由約 1,535 個中文字縮至約 715 個中文字，保留主要操作與檢查方法。
- 第 5 次使用更新後的 Blog 架構，完整重跑兩個案例。主 Agent 對照原文與兩張驗收卡，判定四份最後產出通過；結構檢查也通過。

這幾輪首次寫入後仍發現錯誤，都是修正、重檢後才通過，還不能說 Agent 已經能穩定地一次完成。

## 9. 一句簡短心得

最大的差異是能把這次修正的要求留下來，下次換一份材料時，就有規則可以檢查，不必再從頭提醒同一件事。
