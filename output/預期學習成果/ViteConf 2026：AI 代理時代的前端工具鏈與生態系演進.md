## B. 學習筆記

### 代理把「一次夠快」乘成總時間

編碼代理已經能看懂儲存庫、改多個檔案、跑指令和測試，並自己修錯。2025 年，儲存庫規模的代理讓這種做法容易取得。有時下一個 `/goal`，代理會自己跑好幾天。人仍負責監督和審查。直接操作工具的那一方，要的是一致、行為可預測、取得資訊的成本低，以及能判斷自己這次做得對不對。

人在意讀得懂的錯誤、順手的簡寫，以及五種寫法裡挑一種自己喜歡的。存檔後一秒內看到畫面，就常覺得夠了；少掉幾百毫秒，人不一定感覺得到。代理不需要終端機裡給人看的表格，表格會變成雜訊。同一件事的多種設定和簡寫，對代理沒有好處。它寧可只有一種做法，即使程式比較長、比較重複。設定描述的是專案的事實。風格選擇留在人的編輯器裡。這樣非法狀態比較難被寫出來。人要看得懂的介面仍然要留著。對代理的 API，可預測性放在主觀好不好用前面。

代理改完程式還要驗證：跑 linter、型別檢查、測試，或啟動應用來看。HMR 讓改動快點出現在跑著的應用裡，人在看，代理在看瀏覽器時也一樣。它不休息，同一類操作會重複非常多次，多個代理平行時成本再乘一次。多等的每一秒都進總時間。驗證變便宜之後，它負擔得起更常驗證、每次改更小、更早抓錯。投影片上的時間線是概念示意。

人用的工具現在仍是代理的驗證方式：呼叫它們，再自己讀輸出。改完之後，它真正要的一個問題是：這次改動弄壞了什麼。工具鏈可以知道哪些模組受影響、該跑哪些檢查、哪些測試相關，並回傳帶精確位置、穩定錯誤識別碼和足夠上下文的結構化診斷。通過檢查提供的是哪些項目已被驗證、哪些還沒有。這是要做的介面，這場沒有給出已經能呼叫的指令。

不穩定測試對人是重跑一次再繼續。對代理，它可能以為自己的實作錯了，開始改本來沒問題的程式，耗掉時間和 token，還可能改出真正的退化；另一種反應是連跑多次直到通過，驗證時間會被拉得很長，講者用「大約四倍」描述這種重跑。Vitest 是他們想處理這件事的地方。具體解法還沒有。想要的方向是更強的隔離、控制時鐘和亂數、可預測的非同步，以及把不穩定失敗當成一等結果。驗證可不可信，和速度快慢同一級。

編譯器和語言伺服器已經有語法樹、模組相依、符號定義、引用和型別。代理若只用純文字搜尋重讀檔案，是在把這些資訊再發現一次。除錯也一樣：現在常把瀏覽器主控台錯誤轉到終端機。更進一步的想法是，代理直接查一次請求發生了什麼、帶執行上下文看例外、找出時間花在哪。現況常是用操作電腦的方式打開瀏覽器、重跑、再倒出 CPU 剖析。有些能力要改 runtime，有些也許靠工具鏈的 instrumentation。這些仍是方向。

分開執行的 CLI 會重複讀檔、解析和建立模組圖。build 和 lint 分開跑，兩個指令都再做一次，成本約為兩次。一次驗證若跑 lint、format、test、build 四個指令，工作約為四次。想像是只解析一次，做出緊湊的中間表示，多個工具直接在上面做，並以很少的複製在執行緒之間共用。這不表示一定要單一語言或單一執行檔，可以建在 Oxc 上。講者把它說成高層探索。型別檢查、擴充性、可組合性和相容性仍是開放問題。多個代理在多個 Git worktree 平行時，每個工作樹還會重複安裝相依、重複跑任務。更遠的想法是常駐服務保住共用基底的模組圖，編集後只更新受影響的部分，共用部分用內容位址的不可變結構跨工作樹共用。他說要先有涵蓋完整迴圈的評測：看懂儲存庫、修改、檢查、診斷失敗、得到人接受的結果，量到被接受的時間、工具成本、重試、token、驗證成本，以及多常去追不穩定測試。微基準看不出這些。這套評測被說成大想法之前要先做的事，這場沒有說已經做好。

進 Cloudflare 的前四個月，開源工具仍不綁廠商，出了超過 80 個版本，包含 Vite+ 1.0 和 Vitest 5。Vite 從 2020 年開始，為的是縮短從開發伺服器到瀏覽器裡看見修改的迴圈。

### 已收斂的工具和仍要自己拼的部分

新專案在寫商業邏輯之前，會先付幾種稅：挑選工具、讓 JSON 和 JavaScript 等格式並存、把工具接起來且不互相蓋掉、等待工具跑完，以及應付破壞性更新和沒人維護的外掛。舊組合裡被點名的有 ESLint、Prettier、lint-staged、Husky、nvm。等待被說成 Vite 8 改用 Rolldown 的原因之一。換成 Oxlint、Oxfmt 這類多半用 Rust 寫的工具，等待會下降，選型和接線仍在。

Vite+ 把這些下一代替工具包在一起，預設可以零設定，設定收成一份。Node 版本、套件管理器和 git hooks 是選用。它有 monorepo 任務和快取，也能用於函式庫、CLI，以及用其他方式建置的應用。遷移指令是 `vp migrate`，可以把既有的 ESLint JSX 規則和 Prettier 設定帶過去，也可以交給代理做手動的部分。之後可以用 `vp lint`、`vp format`、`vp check`。Oxlint 以及包住它的 Vite+ 能做會看型別的 lint；型別檢查因為在同一行程裡做，所以少一次行程啟動。`const a = 1` 未使用會被指出；把數字改成字串，`vp run lint` 會給出 TypeScript 錯誤；改名成底線開頭後，未使用消失，型別錯誤還在。

Oxfmt 在 JavaScript 和 TypeScript 上被說成和 Prettier 行為一致，不一致就該當 bug。Oxlint 可用 JavaScript 版和已移植的原生 ESLint 外掛。Rust 版的 React compiler 移植放在 Vite 的 React 外掛裡。Vue、Svelte、Angular 的模板 lint 還在做。Astro 支援還在做，並和 Astro 團隊一起。JavaScript 自訂規則目前拿不到自訂型別資訊：規則若要知道變數是某種型別，現在做不到。遠端快取、`vp release`、`vp docs` 還在計畫。全域安裝後可以釘 Node 版本。示範裡把專案釘在當時解析到的 LTS 24.21.0，機器上沒有的版本會自動下載。

Vite 8 由 Oxc 和 Rolldown 驅動。API 看起來相同，被說成其實是新的建置工具。推出約六個月時，新堆疊的下載被說成離一半不遠，沒有精確比例。

### 部署時少問代理的問題

Void 同時是 SDK、CLI 和部署到 Cloudflare 的平台。`pnpm install void` 之後，套件帶 Vite 外掛和框架接頭。從 `void/db` 匯入資料庫時，測試環境給本地資料庫，`void deploy` 時提供正式環境的資料庫。型別從資料庫 schema 接到客戶端元件。官方接頭包含 React 和 Solid；既有框架的路由可以留著，再讓 Void 在部署時推斷資源。路由接上 React 的 transitions、Suspense 和 actions。沒有用 SDK 的既有 Vite 應用，也可以對它跑 `void deploy`。

代理若被告知使用 Void 並描述要做的功能，就不必再問要用哪一家資料庫、部署到哪裡。`void platform install` 把平台裝進公司的 Cloudflare 帳號，`void connect` 再把應用接到那個平台，由 IT 管誰能部署、專案資源上限和用量。設計師出原型、營運出儀表板、工程師做產品，可以落在同一個平台。它被說成目前開源，可以 fork。更好的抽象會讓 token 變少，這句沒有數字。

Cloudflare 的 Vite 外掛第二版在 beta，並和新的 `cf` CLI 一起。一年前每週下載約 19.6 萬，現場說成約 486 萬，大約 25 倍。第二版和 Wrangler 脫鉤，改與 `cf` 共用 `cloudflare.config.ts`。設定用 TypeScript 寫，worker 的匯出型別留在設定裡，開發或建置時產生推斷用的型別檔。`define config` 可以是物件，或是看得到 Vite `mode` 的函式，用分支選測試或正式環境，不必為每個環境複製一整塊靜態設定。一些已遷移的專案裡，設定最多小了 40%。建置產出結構化目錄，`cf` 消費這個結果，不必重做框架的建置。`cf` 覆蓋的 API 操作從大約 280 增到超過 3000。有了它之後，開發 Cloudflare Workers 的預設路徑走 Vite。

### 解析、列印、資源網址和測試占比

所有坐在 Oxc 上面的工具都受解析速度影響。傳統解析器一次拉一個 token，詞法和語法黏在一起。`/` 是正規表示式還是除法，要看解析狀態，所以不能在不知道前一個位元組時直接向量化。量測過的現代解析器裡，token 轉成結構最久；分支預測失敗約 3.3%，被估計占全部工作的 10% 到 20% 或更多。改跳躍表、把單一演算法向量化、預先配對括號，都比原來更慢。

約 95% 到 99% 的位元組不需要上下文。Classify、Carve、Compress 先用 SIMD 一次看 64 個字元，標出 token 的起迄；Carve 只用大約 1% 到 5% 的內容處理字串、註解、模板字串、正規表示式和 JSX；Compress 再平行壓成 token 陣列。詞法階段大約每秒 6 到 7 GB，文字轉 token 大約快五倍。先做完詞法再解析之後，分支數減半，預測失敗大約降 40%，95% 的檔案解析大約快兩倍。這是與 Oxc 合作的原型。詞法加速排在年底前，貫穿解析器的結構改進在那之後。

Oxc 的解析、轉換、印回程式碼都在 Rust 端。印表器相對不重，把很大的語法樹從 JavaScript 送到 Rust，可能比在 JavaScript 裡直接印還久。從 JavaScript 呼叫 SWC 這類 Rust 印表器時，轉移成本顯出來。所以 Oxc 的 codegen 印表器選 JavaScript，並處理 JSX、TypeScript、TSX，通過約 5 萬個測試。模型先做出和當時最快實作同級的版本。之後的加速來自少看整份輸出：V8 把字串串接做成 rope，可是每次讀輸出的最後一個字元，就要把 rope 展平複製。改為記住剛印出的片段屬於哪一類，最熱的函式大約快 4 倍；真正影響印表的前一項大約 10 類，再快約 20%。箭頭函式回傳物件必須加括號，否則 `{` 會被當成區塊。這類旗標收進同一個 0 到 14 的數字。後續還有約 20%、10%、5%、3%，加總約再快 2 倍。

Vite 8.3 以前，匯入靜態資源或 `new URL(..., import.meta.url)` 時，相對網址要等分塊產生才知道，所以在 transform 鉤子放自訂佔位符，等 Rolldown 產生分塊後在 render chunk 鉤子換成真正網址。外掛若要尊重 Vite 的 base 等選項，就得依賴 Vite 專用行為；相對 base、非 ESM 輸出還有一段從 Rollup 複製的程式；分塊要在 JavaScript 側處理，記憶體多一點。8.3 改由 Rolldown 的 `import.meta.ROLLDOWN_FILE_URL_<referenceId>` 負責替換，Vite 在 `resolveFileUrl` 裡仍依自己的選項組網址。同一個檔在瀏覽器要一個取得得到的網址，在伺服器要另一個相對檔案的路徑，所以佔位符帶兩個 id。沒有 Vite 專用程式的外掛，在 8.3 以上也會尊重這些選項。已知限制是小檔還不會因此內嵌成 data URL。`emitFile` 在未打包的開發模式不能用，那種情況要另外處理。

Vitest 的預設偏向讓測試跑得起來，不保證最快。耗時現在印成百分比，最耗時的在前。轉換最大，可能是某個外掛很慢。匯入最大，可能是模組圖太大，或桶檔案把大檔一起拉進來。測試本身最大，表示該看測試在等什麼。`vitest doctor` 會試已知影響效能的設定；隔離若讓測試失敗，那個選項不會被算成最佳。關掉 `isolate` 有機會快兩到三倍，但要自己清全域狀態、關掉伺服器、取消殘留 callback。預設是每個測試檔結束 worker 再起一個，所以隔離開著時這件事由 Vitest 做。

JSDOM 這類環境，在講者的筆電上光匯入就要約半秒。預設每個測試檔都要一份新的 JSDOM。VM threads 和 VM forks 讓每個 worker 只匯入一次，每個測試檔只付設定成本。修掉會讓 worker 太常重建的記憶體洩漏之後，相對路徑又帶副檔名的解析改走預設 URL，解析占比從約 30% 降到約 2%，對照前一版大約快 50%。多數 Vitest 自己的套件被打進執行器，減少桶檔案；spy、runner、snapshot、expect 仍是一般套件。使用 JSDOM 時，現在的建議是 VM pools。更理想的是瀏覽器模式，它稍慢，這句沒有對照數字。

檔案系統模組快取在 Vitest 5 變成穩定。上千個測試平行跑時，轉換很少是瓶頸，快取幾乎看不見。只跑一個測試檔、模組超過一千個時，他看過要等 2 到 7 秒才開始；開快取後幾乎立刻開始，檔案仍要執行。內嵌子專案以前可能各開一個 Vite 伺服器，例子裡是三個。共用伺服器現在預設開啟，單元測試和整合測試共用轉換結果。

`bench` 從測試情境取出，必須再呼叫 `run` 才有統計，多個 benchmark 串行，刻意不平行，以降低變異。結果可以互相比，用來抓退化。哪個比較快，reporter 這時還沒顯示，被說成會修的 bug。巢狀子專案不必再全部寫在根上。`vi.when` 用和 `toEqual` 相同的相等檢查來寫「用這些引數呼叫時回傳什麼」，並能檢查每一組引數都被呼叫過。瀏覽器模式有內建 trace，由 artifact API 露出。把 CommonJS 全域變數塞進測試執行器，對瀏覽器和 JSDOM 有用，對 Node 應用會製造假陽性：測試通過、應用其實起不來。拿掉這層被排到 Vitest 6，現在可以用一個設成 false 的選項先試，鍵名這場沒有念完。

開發期和建置期可以同一個設定打開檢視：每個外掛處理了哪些模組、鉤子次數和時間、單一模組逐步的程式差異；建置側能看模組路徑、分塊大小、套件占比、重複版本，以及修改前後的體積。Vitest 的既有介面、Oxlint 和 Oxfmt 被放進同一個畫面。外掛在 setup 裡註冊自己的網址和圖示就能掛上。跨框架的部分是先定義一次工具，再接到不同框架的請求處理器。

### 框架邊界、獨立部署和給代理的規範

元框架過去補的是核心沒有的伺服器渲染和路由。Solid 2.0 把端到端型別的 server functions、會看 Vite manifest 的串流、head，以及一次往返同時做變更和重新驗證的協定放進核心。路由和快取策略留給 TanStack Router、TanStack Query 或自訂組合。檔案路由和預渲染是與框架無關的 Vite 外掛。部署收成一個 fetch 處理器。第一天可以是單頁應用，要串流就開 SSR，要伺服器函式就再開一個旗標。整個應用只有一條請求和一條中介軟體鏈，所以認證或錯誤監控的整合按 Solid 做一份，不必按每個上層路由各做一份。Solid 2.0 的反應式基本單元可以接受 promise 或 async iterator。

每個全端框架乘每個雲端平台，會變成一格一個套件。Netlify 的 Vite 外掛在 `writeBundle` 之後讀伺服器產物，約 99 行，被說成完整支援 TanStack Start，並支撐該平台上數十萬個這類網站；Solid Start 2 釋出後這支外掛直接能用。它依賴幾個假設：恰好一個進入點分塊、那個分塊就是伺服器進入點、預設匯出上有 fetch、所有路由走這一個處理器。Vite 產物裡看不出哪個檔能接請求，多入口和路由中介資料也還沒有標準欄位。版本錯位是舊分頁在新部署後去抓已經不在的雜湊分塊；把版本 id 放進客戶端、用標頭或 cookie 讓伺服器回答對應版本，仍是提案，有實作和 RFC，這場沒有說已經上線。投影片上「105 個外掛對 7 個」是簡報裡的對照。

Nitro 3 把底層 HTTP 框架改到 Web 的 Request、Response、Headers，路由在建置時編成純函式，目錄結構不進正式環境。無法打包的原生模組由追蹤把必要檔案複製進輸出。套件體積被說成從 100 MB、alpha 約 9 MB，到現在往 5 MB 以下。`vite build` 產出可攜目錄。追蹤用的是 Node、Deno、Bun 和 Cloudflare Workers 都有的診斷通道，由框架自己登記 span，打開旗標才收集。Vitest 整合會為每個測試檔啟動一個隔離的真實伺服器，測完拆掉。Nitro 3 這場仍在走向穩定版。

Qwik 在建置期依 `$` 邊界把程式拆成小段，伺服器把可恢復的快照放進 HTML，瀏覽器先把片段放進快取，互動時才執行該次需要的片段。這是延遲執行。片段可以先放進快取，執行等到該次互動。Qwik 1 的加權分數是 2.59，Qwik 2 是 1.23，低分較好。Rakuten 對相同頁面做 A/B，轉換多 33%，每位訪客營收多 53%。另一個被引用的案例把放棄載入從 3.8% 降到 0.9%。Qwik 2 改由 Vite 8 和 Rolldown 驅動，優化器從 Rust 加 SWC 往 TypeScript 重寫，已發布的應用仍預設用 Rust 優化器。RC 已出。代理若自己重複做程式碼拆分，會消耗 token；互動若仍要整頁水合，拆分有一個它過不去的上限。

多頁應用的歷史導覽幾乎免費得到往返快取。痛點是每次連結或表單都整頁重載，暫時狀態會掉。Marko 的實驗功能在 Vite 設定把 patches 設為 true 之後，導覽改回傳描述頁面差異的 JSON，伺服器不必知道客戶端目前狀態，失敗則退回一般導覽。範例重載後進來的 JavaScript 被說成 7 KB 和 12 KB，再加上那個輸入框的程式。

Svelte 的編譯器能在元件裡直接 await，並把多個 promise 改寫成 `Promise.all`。尚未釋出的 custom renderer 從 `createRenderer` 實作建立節點、插入、刪除、屬性和事件。示範用 Vite 的 environment API 把元件渲染成檔案系統裡的檔案，講者說這個示範本身不實用，它用來指出同一套元件可以接到原生介面、終端機或桌面。PR 編號被說成 18042。

多團隊綁成一次大部署時，一個團隊的不穩定測試會擋住其他人。Module Federation 的 Vite 外掛讓各團隊自己建置和部署，外層 shell 不用重建。它處理的是團隊交付速度互相卡住。建置體積要另找做法。Vite 5 到 7 走 Rollup，Vite 8 走 Rolldown，外掛內部約 30% 在處理兩套引擎和分塊清單，約 25% 在處理單例和版本查找，約 14% 在 SSR。驗證庫涵蓋超過 12 個框架。下載量被說成每月近 400 萬。Vite 團隊正式推薦這支外掛。

Storybook 11 讓支援的框架都建在 Vite 上，並用外掛、skills 和 MCP 讓代理先讀設計系統文件再產生 stories。示範裡，代理依規範改用既有的表面 token，分隔元件沒有被新做一個，並給出按變更理由分組的審查。他們的基準是：最多快 41%、工作階段最多便宜 31%、程式變更最多小 19%。樣本數和對照方法這場沒有講。

### 維護者、issue 和文件範圍

約 70% 的開源維護者單獨或在極小團隊工作。2024 年的調查裡，60% 當年離開過或考慮離開一個專案。各主要語言的頂尖套件中，約 12% 被稱為表面還能安裝、實質停更，另約 20% 休眠到令人擔心。至少四起全球重大安全事件和維護者過勞有關，被點名的是 Heartbleed 時的 OpenSSL，以及 XZ Utils 的後門。約 60% 的開源開發者沒有報酬，另 16% 有報酬但不夠生活。AI 讓開 issue 和送報告變容易。curl 的 Daniel Stenberg 在團隊被這類報告淹沒後，結束該專案的漏洞懸賞。Open Source Pledge 的加入條件是公司每年為每位開發者至少給開源專案 2000 美元。募到的總額在錄音裡聽成重疊的數字，這裡不引用總額。個人能做的是先看專案的 AI 政策，並不要提交自己看不懂的程式碼。

Astro 不用讓 backlog 無限成長，也不用六個月沒動就關掉的機器人。流程先寫成 markdown 的 agent skill：重現、診斷、判斷是不是缺陷、再寫失敗測試並修。每步在隔離的子代理裡跑，各自寫報告。接著變成 GitHub 標籤驅動的狀態機，用 package.pr.new 給回報者一個可安裝的預覽套件，順利時約 15 到 20 分鐘從 issue 到 PR。未決 issue 從高點 250 降到 0，多數時間維持在 10 以下。有一個 HMR 條件被代理反覆改壞，維護者補上一行說明為什麼要這樣寫，之後代理不再改它。這套流程後來抽成可從 Slack 或排程觸發、與平台和模型分開的事件框架。

npm 供應鏈的例子包含設定錯誤的 CI 洩漏密鑰、釣魚後發布帶惡意安裝腳本的版本，以及 CI 的 node_modules 快取被下毒。GitHub Actions 被說成目前常見的攻擊面：`pull_request_target` 在有基礎儲存庫機密的環境跑外部 PR 程式；checkout 把憑證留在磁碟；用可被假造的使用者名稱做條件；權限大於需要；只釘可變標籤、不釘 commit hash；把使用者輸入嵌進 shell。chalk 被說成每週 4.91 億次下載，並在先前的一年被入侵，同一位維護者能碰到的其他套件一起中招。緩和做法裡講清楚的有：應用和函式庫都提交 lockfile；Renovate 或 Dependabot 用批次更新，一般更新有 5 天冷卻，安全修正仍有別的路徑；npm 和 pnpm 可設最短發布年齡，例子是 2 天；預設不跑安裝腳本，再按套件和版本放行；pnpm 可拒絕信任等級下降的新版本，npm 沒有這項。把 Actions 釘成 hash 的工具，以及在 CI 裡掃描 workflow 的 linter，錄音裡的名字不穩。能用 Node 內建能力就少一個相依，被舉的例子是 Node 已有的 style text，用來取代 chalk 這類套件。

文件的最低標準是清楚、正確、找得到、走得通。六個要求是：只寫現在怎麼用、短、步驟完整、結構一致、先寫最常見的成功路徑、只寫這個專案負責的範圍。RSS 外掛只寫安裝、設定和怎麼把 feed 加進部落格。新功能若只出現在部落格、新 API 若只出現在發行說明，仍然該進文件。極端排障步驟有可能被人或代理當成每個人都要做的清單。

## C. 自我驗證

### 解釋取捨

1. 人覺得存檔後一秒內更新就夠、不穩定測試重跑一次即可。這兩件事在代理的驗證迴圈裡會變成什麼成本？
2. Vitest 把耗時印成環境、匯入、轉換、測試四段百分比。轉換最高和匯入最高，各自先查什麼？關掉 `isolate` 之前要自己負責什麼？
3. Vite 8.3 為什麼不再在 JavaScript 的 render chunk 鉤子裡替換資源佔位符？小檔內嵌這件事現在停在哪裡？
4. Solid 把 server functions 放進核心、Netlify 用約 99 行的 Vite 外掛接上兩個框架。後者還沒有、所以還不能通吃所有框架的資訊是什麼？

### 拿到一個專案來判斷

1. 列出這個專案一次驗證會呼叫的指令。哪些會各自讀檔、解析、建模組圖？其中有沒有已經在同一行程裡做完格式、lint 和型別檢查的指令？
2. 看一份 GitHub Actions workflow，標出有沒有 `pull_request_target`、只釘標籤的 action、以及大於需要的寫入權限。npm 或 pnpm 有沒有最短發布年齡和安裝腳本的允許清單？
3. 拿一份技術文件，標出哪些段落在寫現在的用法，哪些是舊版故事、行銷句子，或把罕見故障寫成每個人都要做的步驟。

### 做一次測量

1. 在一個 JavaScript 專案跑一次測試，記下耗時百分比的順序，以及 doctor 若建議改隔離或 VM pool，你接受或拒絕的理由。再找一個代理改錯過的條件，補上這段條件為什麼存在的一句話，下一次讓代理改到附近時看它還會不會改掉。

## D. 尚未解決的問題

- **共用中間表示和跨工作樹常駐服務還沒有可安裝的實作。** 型別檢查和擴充若進不了同一份表示，驗證迴圈仍會退回多個行程各自解析。這被說成高層探索，型別檢查、擴充性、可組合性和相容性是開放問題，而且要先有完整迴圈的評測，這場沒有說評測已經做好。
- **不穩定測試還沒有具體修法。** 代理會把時好時壞的失敗當成自己的程式錯了，或連跑多次把時間拉長。講者說 Vitest 是處理這件事的位置，同時說現在沒有具體解法，只列出隔離、時鐘、亂數、可預測的非同步，以及一等的不穩定失敗識別。
- **單一平台外掛要接上所有框架，還缺伺服器進入點、路由和版本錯位的標準欄位。** 沒有這些欄位，外掛只能假設恰好一個進入點、而且那個進入點有 fetch。約 99 行的 Netlify 外掛在 TanStack Start 和 Solid Start 2 上被說成能用，講者也說這四個假設擴不到其他框架。版本錯位的共用 schema 有 RFC，這場沒有說已經上線。
- **若干工具名、公司名和募款總額在錄音裡不能當成正式名稱。** 寫錯名字會讓讀者去裝一個不存在的套件，或引用一個沒有說清的金額。最短發布年齡、5 天冷卻、lockfile、安裝腳本允許清單、2000 美元的 pledge 條件是聽得清的。把 Actions 釘 hash 的工具、掃描 workflow 的 linter、事件框架的拼法，以及 pledge 的總額，錄音重疊或口語化，不能寫成已核對的套件名或金額。
- **如何檢查代理的驗證迴圈會不會重複解析、把不穩定測試當成程式錯誤，適合寫成一篇給團隊的檢查文章。** 很多團隊已經讓代理跑既有的 lint、測試和 CI，人的一秒標準和重跑一次的習慣會被乘進總時間。這場有四個指令約四次工作、Vitest 的百分比、以及不穩定測試尚無解法，可以直接變成檢查步驟，同時把共用引擎留在尚未出貨的範圍。
